# Delta: Agent-Agnostic Symphony

Every difference between upstream `../SPEC.md` and this fork's `SPEC.md`, in order of appearance in
the document. Nothing else differs: `SPEC.md` is generated by applying this file, and
`bun run spec:check` fails if it ever stops being.

`RULES.md` explains the format, the execution model, and what to do when upstream changes. Read it
before editing this file.

```delta-meta
upstream: ../SPEC.md
output: SPEC.md
lock: upstream.lock.json
```

## The change in one paragraph

Upstream Symphony orchestrates *Codex*. The orchestrator speaks the Codex app-server protocol, its
config block is named `codex`, its runtime metrics are named after Codex, and its conformance tests
assert Codex message shapes. This fork keeps every scheduling, workspace, tracker, and observability
rule exactly as upstream wrote it, and replaces the one coupling: the coding agent now sits behind an
`Agent Adapter` chosen by `runner.kind`, in the same shape upstream already uses for issue trackers.
Codex becomes one adapter (`codex-app-server`) rather than the only possibility, and a workflow that
uses upstream's `codex:` block keeps working unchanged.

## Ordering rule

Entries appear in upstream document order, and ops execute in that order. Every `FIND` anchor and
`section:` heading is therefore written in **upstream** terms. IDs are allocated in creation order
and never renumbered, so position in this file — not ID order — is what determines execution. The
one global rename table (`D-019`) is always last regardless of its number, so it only sees text no
patch has already replaced. This is why several
identifiers that appear many times upstream have small `expect` counts here: the other occurrences
were already consumed by a structural patch.

## D-002 — Goals and non-goals for a replaceable agent

Adds two goals — integrate coding agents through a replaceable adapter, and switch agents by editing
configuration — and two non-goals that fence off the failure mode this design invites: the
orchestrator does not normalize coding-agent feature sets, and does not define a portable agent wire
protocol. Adapters declare what they support; the orchestrator picks a documented fallback.

## D-006 — `runner` replaces the `codex` front-matter block

Introduces the `runner` block: `kind` selects an adapter, `provider` is adapter-owned and passed
through verbatim, `env` carries agent-runtime credentials to the child, `require_client_tools` turns
a silent capability downgrade into a loud preflight failure, and the three timeout fields stay core
because the orchestrator enforces them. Codex's `approval_policy`, `thread_sandbox`, and
`turn_sandbox_policy` are no longer core config; they are ordinary `runner.provider` keys.

The upstream `codex` block is kept as a deprecated alias with a fully specified normalization, so an
unmodified upstream `WORKFLOW.md` runs on this fork and produces upstream behavior. `runner` wins if
both are present, with a warning, and the two are never merged.

## D-008 — Continuation turns follow a capability, not a vendor

Upstream tells the worker to send continuation guidance only, because Codex keeps thread history.
That is wrong for an agent that keeps nothing. The fork makes the decision follow the adapter's
`session_continuation` capability: guidance only when the agent remembers, the full rendered prompt
again when it does not. Both paths remain multi-turn, because the workspace — not the agent's
memory — is what actually carries state between turns.

## D-009 — Stall detection against non-streaming agents

Stall detection measures event silence, which assumes the agent streams events. For an adapter that
declares `streaming_events=false` the only events are session start and turn end, so the same
timeout silently becomes a whole-turn wall-clock cap. The fork states that consequence instead of
leaving operators to discover it.

Upstream anchor: 8.5.

## D-010 — Workspace confinement without a subprocess

Upstream's first safety invariant is written as a check on subprocess `cwd`. An adapter may drive a
remote or in-process runtime and never launch a subprocess, which would make the invariant vacuous.
The fork keeps the subprocess check verbatim and adds the obligation for every other adapter: confine
all agent file operations to the workspace, refuse a session whose working directory is anything
else, and document how. An adapter that cannot state this does not get to start a session.

## D-011 — Agent Runtime Integration Contract

The substance of the fork. Upstream section 10 is the Codex app-server protocol section; it is
replaced by a portable contract with the same responsibilities.

- **10.1** an adapter registry keyed by `runner.kind`, with adapter, config, and capabilities bound
  to a session snapshot at start, and no implicit selection by probing the host.
- **10.2** six required operations — `capabilities`, `validate_config`,
  `sensitive_environment_names`, `start_session`, `run_turn`, `stop_session` — with normalized
  parameters and a `TurnOutcome` whose only success status is `completed`.
- **10.3** seven capabilities, each with a *normative* fallback: `session_continuation`,
  `streaming_events`, `client_tools`, `approvals`, `cancellation`, `usage_reporting`,
  `rate_limit_reporting`. This is what makes the boundary real rather than decorative — the
  orchestrator never inspects the adapter's name, and an adapter that declares a capability it does
  not honor is non-conforming.
- **10.4-10.5** startup and turn responsibilities, with the completion mapping every adapter must
  implement, and the requirement that `session_key` stays stable even for adapters that re-create
  runtime state between turns.
- **10.6** the normalized event vocabulary. Orchestrator logic may depend on nothing else; native
  signals with no equivalent map to `notification` or `other_message`.
- **10.7** approval, tool-call, and user-input policy, with client tools gated on the capability and
  the tracker-tool hooks carried over from upstream unchanged.
- **10.8** timeouts and error categories, using upstream's tracker-adapter error convention.
- **10.9** the Agent Runner algorithm, including the rule that only the runner may hold an
  adapter handle — orchestrator state stores normalized metadata, never a vendor object.
- **10.10** the adapter profile publication requirement, mirroring the tracker adapter profile in
  11.2. A capability set without a published profile is not verifiable.

Upstream anchor: 10 (all of it).

## D-012 — Tracker writes depend on an agent capability

Upstream's tracker-write boundary assumes the agent can call host-provided tools, which is a Codex
capability, not a universal one. The fork states the dependency explicitly, says what happens when
the selected adapter cannot call tools (the tools are not advertised and the workflow owns tracker
writes another way), and points at `runner.require_client_tools` for deployments where that downgrade
must be an error instead.

## D-013 — Observability: snapshots, token accounting, JSON API

Three related changes.

The runtime snapshot gains `agent_kind` and per-row `usage_reported`, so an operator can tell which
agent produced a session and whether its zeros are real.

Token accounting stops describing Codex payload shapes. Extraction moves into the adapter, which
normalizes usage into the section 10.6 event and labels it `cumulative` or `incremental`; the
orchestrator accumulates by mode. An adapter whose runtime is ambiguous must omit the report rather
than guess, because a missing number is recoverable and a wrong total is not.

The JSON API example gains `agent_kind` and `usage_reported` and drops the thread-shaped session ID.

## D-015 — Secret handling and harness hardening

Documents `runner.env` as the one channel that intentionally passes a secret to the agent child, and
introduces the agent adapter's `sensitive_environment_names()` as a *redaction* contract, kept
distinct from the tracker adapter's `secret_environment_names()`, which is a *removal* contract.

Generalizes the hardening section beyond Codex and adds the warning this design makes necessary:
making the runtime pluggable widens the attack surface rather than narrowing it, because adapters
differ in what controls they offer and some offer none. Switching `runner.kind` does not preserve a
security posture, and for a runtime with no built-in policy controls, external isolation is the only
control there is.

## D-020 — SSH worker extension composes only with subprocess adapters

Upstream's SSH worker appendix assumes the coding agent is a local subprocess whose stdio can be
tunnelled. That is true of the Codex adapter and of most CLI-shaped agents, and false of an adapter
that reaches its runtime over HTTP or runs in-process. The fork keeps the stdio model as the normal
case and requires every adapter to state whether it supports remote workers — and, if it does not,
to fail startup with `agent_capability_unsupported` rather than quietly running the agent on the
orchestrator host while the workspace lives on another machine.

Also generalizes the host prerequisites: what a remote host must provide now depends on
`runner.kind`, and changing that key changes the prerequisites on every host in the pool at once.

Upstream anchor: A.1, A.3.
